# 60 FPS: can the port offer it? (2026-11-13)

A player asked for 60 FPS. They said Run Speed helps but the game "still flickers", and that Felix's mod runs at 60 and plays more smoothly.

**Answer:** yes. The way to do it is to keep the logic at its stock 20 Hz and draw in-between frames with the game's own draw code, using the framework's render passes. The other options are worse. Running the logic at 60 Hz would mean auditing the whole game. Smooth motion (`[video] frame_generation`) already runs on DW, but it cannot move the 2D field background. The "flicker" is the game's 20 FPS, made more visible by Run Speed's bigger and uneven steps. The game has no sprite flicker.

Tags: `[run]` was measured in the game today from `build-60fps`. `[read]` was read in source. `[doc]` comes from framework docs. `[Horizon]` comes from the public README.

## 1. How the game paces itself

- **One logic tick and one drawn frame every 3 VBlanks: 20 FPS, in the field and in battle.** `gameLoop` runs input, `tickScript`, `tickObjects`, `renderObjects`, `DrawSync`, `VSync(3)`, swap and `GsDrawOt` (`src/main/main.c:3933-3963`). Battle uses the same pattern: `BTL_battleTickFrame` ends in `VSync(3)` (`src/btl/battle_main.c:2595-2611`). See also GAME.md 10.1. `[read]`
  - Measured with the presenter's ring (`gl_present_ring`) over 300 presents per phase. Field idle: 297 of 299 flips 3 VBlanks apart. Running: 298 of 298. Battle: 297 of 299. The odd gaps are loads. Guest VBlank is 59.93-60.0 Hz, and the logic counter `PLAYTIME_FRAMES` advances 19.8-20.0 per second. `[run]`
  - The game never ran at 30. The title and main menu use `VSync(0)` (GAME.md 10.1).
- **No frame-skip.** `VSync(3)` waits for the third VBlank since the last call. A slow tick would just give 15 FPS for a while (INTERNALS: Run Speed's "lagging frames"). None showed up in today's flips. `[run]`
- **Everything counts ticks**, so changing the tick rate changes game speed:
  - Movement is root motion from `tickAnimation`: 50 units per tick when running, 20 when walking (INTERNALS, Run Speed).
  - Animation streams are keyframes counted in ticks (GAME.md 11.2, `src/main/anim.c:303-347`). Map sprite animations hold for N ticks (`src/main/overworld.c:490-545`).
  - The clock adds one in-game minute every 20 ticks, i.e. every real second (`src/main/clock.c:116-136`).
  - Battle: the speed gauge fills every other tick (`src/btl/battle_main.c:1640-1650`). AI, effects and the run-off are all counted in ticks (GAME.md 7).
  - Field mist drifts 1 px every other tick (`src/main/overworld.c:567`, `:586`). Texture animations step on even ticks (`src/main/anim.c:104-113`).
  - The camera follow and background tile streaming run inside the map's **render** callback: `renderMap` calls `tickCameraFollowPlayer` first (`src/main/map.c:3949-3960`), which calls `updateTileRow`/`Column` with `LoadImage` (`:4688-4808`, `:5195-5275`). `[read]`
- **Run Speed** (INTERNALS 4.3) gives the tamer whole extra stock ticks of movement: an extra `tickAnimation`, `tickCameraFollowPlayer` and `tamerTickWalkingState`. At 2x that is 100 units per drawn frame. At 1.5x it alternates 100 and 50, keyed on odd VBlank counts. The frame rate stays at 20.
- **World Clock Speed** pins `tickGameClock`'s speed read to the game's own half or double mode (`0x800DD008`, `src/main/clock.c:116-136`). It has nothing to do with frame rate.
- **How the runtime presents:**
  - It paces guest VBlanks on the wall clock at 59.94 Hz and presents each one. On this machine's 165 Hz panel it logs "synchronized swaps on 165 Hz panel". `[run]`
  - A 50 ms game frame on 165 Hz lasts 8.25 refreshes, so it is held for 8 or 9 (48.5 or 54.5 ms). That is uneven by about 12%. `[inferred]` On a 60 Hz panel each frame is held for exactly 3 refreshes.
  - In the stock run, host-side gaps between flips were 39-67 ms, while my polling loaded the machine. With the render thread they were 49-51 ms. `[run]`

## 2. The flickering

| Candidate | Verdict |
|---|---|
| Sprites drawn on odd/even frames | **No.** Every per-tick parity test in field and battle code is about timing (mist, texture animation, speed gauge, clock), not visibility (`anim.c:104`, `overworld.c:567`, `battle_main.c:1642`, `clock.c:123-134`). The deliberate blinks are the menu cursor (`PLAYTIME_FRAMES % 10 < 5`, `game_menu.c:1449`, `:2505`) and the disliked-map status icon (GAME.md 8.7). `[read]` |
| Transparency done by flicker | **No.** The game uses the GPU's real semi-transparency, and no draw path alternates. `[read]` |
| Frame rate and pacing | **Yes.** At 20 FPS each frame jumps 50 units, and the whole background scrolls in visible steps. Sample-and-hold screens show that as strobing, more so at high refresh. Run Speed makes the step 100 units (2x) or alternately 100/50 (1.5x, an uneven cadence). A non-60 Hz panel adds the 8/9-refresh beat. |

So "flicker" is judder at 20 FPS. It is not a bug that can be fixed on its own. It goes away only with in-between frames.

## 3. Felix's mod

Felix's mod is **Horizon** by Felix Carmona (https://github.com/felixcarmona/dw1horizon, MIT, already listed in GAME.md 1.2). Its README says:

- "Automatic 20/60 frames per second": 20 at normal CPU speed, 60 "with sufficient CPU overclock (250%)".
- "Logic and input stay at 20 Hz."
- "Smoothing at 60 fps displays the picture up to 50 ms later."

So Horizon interpolates the picture between 20 Hz ticks on the console itself. That is why it needs about 2.5x the CPU, and why it adds up to one tick of delay. I read the README only. I copied nothing and downloaded nothing. The README does not say what it interpolates. The player has the facts mixed up: the markisha64 60 FPS patch is for Digimon World 2003, a different game, and its battles stay at 15-20 FPS (romhacking.net hack 8105).

## 4. Options

| | What | Cost | Risk | Verdict |
|---|---|---|---|---|
| (a) | Logic at 60 Hz: `VSync(1)` and every per-tick step divided by **3** (not 2: the game is 20 Hz) | Months. 129 `tick*` functions, 187 `addObject` sites, 89k lines in `src/main` + `src/btl` alone, plus STD/VS/KAR/EVL/fish overlays, script waits, animation and effect data authored at 20 Hz | Very high. Integer steps such as 50 units, gauge +1 every 2 ticks and the clock do not divide by 3, so behaviour drifts. Also breaks DW 1.5 byte-compatibility, Run Speed's parity trick, savestates and every measured fact in GAME.md | No |
| (b) | **Render passes** (`psx_mod_render_pass_*`, RENDER_PASSES.md): at `VSync(3)` entry, redraw `renderObjects` with the camera and bone matrices blended between tick n and n+1, in the framework's sandbox | About 2-3 weeks (breakdown below). The framework already has planning, sandbox, rollback, budget, verification and a worked title (V8:2) | Medium. Logic in the render path, tile streaming at fractional cameras, widescreen hooks firing inside passes | **Yes** |
| (c) | (b) for the field only. Battle and other loops keep stock frames | About 1-1.5 weeks | Low to medium | **Yes, as milestone 1** |
| - | Smooth motion, which exists already (`PSX_FRAME_GEN=1`, FRAME_GENERATION.md) | None | Measured unusable for DW: see below | No |
| - | Crossfade (`psx_mod_set_frame_interpolation`, LINEAR) | Tiny | Ghosting; the image is one frame late; no real motion (FRAME_RATE.md) | No |

**Smooth motion on DW** `[run]`, from `build-60fps/m60/fg/result.json` and its burst PNGs:
- It switched on: 165 Hz, 8 in-between frames planned per flip.
- Idle: every camera fit was rejected ("few pairs", `rejected` = `real` = 1991).
- Running: `verdict_ok` 0 ("few inliers", `cam_shift` 2280).
- Battle: generated frames cost 11.2 ms each. The breaker tripped ("queue backed up") and the plan dropped to 0.
- In the running burst, generated frames changed about 4,000 pixels (the models) and the background did not move. Each real frame changed about 650,000 pixels (the scroll).
- Cause: DW's field is a 2D tile image drawn as POLY_FT4 from `MAP_TILE_DATA.cameraX/Y` (`map.c:3985-4005`), not GTE geometry, so a GTE-based generator cannot move it. The models slide over a background that still steps at 20 Hz.

**Why (b) fits DW** `[read]`/`[doc]`:
- Models are per-bone `GsCOORDINATE2` matrices read by `GsGetLws` in `renderDigimon` (`model.c:2881-2943`, `PositionData` in `include/dw/entity.h:11-17`). That matches the framework's `PSX_MOTION_MATRIX` kind.
- The camera is `GS_VIEWPOINT` (6 i32) plus `MAP_TILE_DATA.cameraX/Y` (i16 scalars).
- The loop is PsyQ double-buffered (draw after swap), which is the framework's `PENDING` flip mode. In-betweens of n→n+1 show while frame n is up, so there should be **no added delay** over stock, against Horizon's up to 50 ms. `[inferred from RENDER_PASSES.md, flip modes]`

## 5. Recommended: render-pass plugin, field first

1. **Package feature.** A `dw.vanilla.qol` (or own package) feature "Smooth 60 FPS" with a rate choice (display / 60 / 120). The manifest declares `vsync = "off"`. Activate it with `psx_mod_activate_render_pass_rate`. About 0.5 day.
2. **Pass point and span.**
   - An entry hook on `VSync` (`0x80091CA8`), called from `gameLoop` (`0x800EFB68`). It ignores entries made inside a pass.
   - An instruction hook at `GsSetOrign` in `gameLoop` records the registers.
   - Each pass replays the span from there to `applyDrawOffset` with `psx_mod_run_guest_span`, then submits the OT into the DISPENV rect. 1-2 days.
3. **Blend state** (`render_pass_motion.h`). 2-3 days.
   - `GS_VIEWPOINT` (`0x80185BA8`) and `MAP_TILE_DATA.cameraX/Y` (`0x8014F084` + 7092).
   - Every placed entity's bone `posMatrix.coord`. Identity is entity pointer + bone + species. The `coord2` `flg` must be cleared so `GsGetLws` recomputes.
   - Limits come from measured motion: 50 units per tick, 100 at Run Speed 2x. Warps and cuts keep their value.
4. **Logic inside render.** In a pass, `tickCameraFollowPlayer` (`0x800D6F64`, called by `renderMap`) must not run, because the blended camera replaces it. Tile columns or rows that change between n and n+1 (`MAP_TILE_X/Y`) can leave an edge without tiles at mid-alpha. Possible fixes: keep the older tile origin until alpha 0.5, or reuse the widescreen tile ladder (`dw_ws_camera.c`). Check that widescreen's entry hooks (`backdrop-align`, `hud-park`, `tile-ladder`) behave inside passes. 1-2 days.
5. **Fallbacks.** Menus, text boxes, evolution (EVL), fishing, FMV, STD/VS/KAR loops, Rewind and netplay show stock frames. The driver already crossfades while passes are unavailable. 1 day.
6. **Battle** (milestone 2). Second pass point at `BTL_battleTickFrame`'s `VSync(3)`. Blend fighters, EFE particles, TMD effects (`effect_common.c:579`) and floating numbers. 2-4 days.
7. **Verification.** 2-3 days.
   - `render_pass_stats` with 0 span failures, and `PSX_RENDER_PASS_VERIFY=1` with `verify_mismatch` 0.
   - `frame_fingerprint` the same with passes on and off.
   - `render_pass_dump` in town, running, Run Speed 1.5x/2x, widescreen 21:9, HD pack, and battle.
   - `--hidden-window` on ports 65xx.

## 6. Risks

- Logic that runs inside draw callbacks besides `renderMap` (camera follow) would advance inside a pass. RAM is restored afterwards, but the image would be wrong. Each `render*` callback that `renderObjects` reaches needs a scan.
- Tile edges at fractional cameras (step 4). Background drawing uses whole pixels, and the camera moves only a few pixels per tick, so sub-tick positions may round to the same image.
- Host cost: three or more replays of `renderObjects` per 50 ms. The budget sheds passes on slow PCs. It needs the OpenGL renderer, and Vulkan or Software users get stock frames.
- Interplay with widescreen, the HD pack, Run Speed (extra camera calls) and DW 1.5 (same executable code, so it should carry over; untested).
- Not checked: whether `GsSetRefView2` running before `tickObjects` (camera one tick behind objects in stock) shows up once both are blended.

## 6b. Prototype (field and battle, 2026-11-13, uncommitted)

This section records the prototype as it stood on 2026-11-13. Section 6c has what changed to ship it. Then, `dw_smooth60.c` was built only with `-DDW_SMOOTH60_PROTO=ON`, and its manifest lived only in `build-60fps/mods/installed/`. Feature `smooth60`, option `rate` = `60` or `display`.

How it works:
- **Pass point: `GsDrawOt` entry, when called from `gameLoop`.** That function is already in `game.toml`'s `mod_function_entry_funcs`, so `generated/` needs no regen. `VSync` is not in that list, which is why the PENDING point was not used.
  - At `GsDrawOt` entry the swap has already shown tick N, so the plugin uses `PSX_MOD_RENDER_PASS_FLIP_SHOWN`. That adds one game frame (50 ms) of delay, the same as Horizon's. Moving to `VSync` entry and PENDING needs `VSync` (`0x80091CA8`) added to the entry list, plus a codegen run.
- **Capture, once per field frame.**
  - Bone `posMatrix.coord` (`PSX_MOTION_MATRIX`) for every on-map entity in `ENTITY_TABLE`, plus bone 0's `location`.
  - `DRAWING_OFFSET_X/Y` and `MAP_TILE_DATA.cameraX/Y`, which the background reads.
  - `DRAWING_OFFSET_*_COPY` and `GS_VIEWPOINT_COPY`, which `gameLoop` gave `GsSetOrign` and `GsSetRefView2`.
  - History is dropped on a map change and outside `GAME_STATE` 0.
- **Each pass:**
  1. Apply the blends and clear each bone's `coord2.flg`.
  2. Point `ACTIVE_FRAMEBUFFER` and `ACTIVE_ORDERING_TABLE` at the shown buffer (1-B).
  3. Call `GsSetWorkBase`, `GsClearOt`, `GsSetOrign`, `GsSetRefView2`, `GsSetProjection`, `renderObjects` and `applyDrawOffset`.
  4. Put one packet at the head of the OT: a fill, the draw area, and the world offset.
  5. Call `GsDrawOt` and `DrawSync`.
  - A filter skips `tickCameraFollowPlayer` inside a pass, so `renderMap` does not move the camera.
- **Buffer origin.** `DR_OFFSETS[b]` holds the buffer origin plus (160, 120). My first build read it as the bare origin, and half the rects came out of range. Fixed.

### Battle passes

How they work:
- **Same pass point.** `GsDrawOt` entry, when called from `BTL_battleTickFrame` (`0x8005DEC4`..`0x8005DFC8`, BTL overlay) with `GAME_STATE` 1. The BTL, STD and VS overlays share that address range, so `GAME_STATE` is what tells them apart. History is dropped when the mode changes.
- **What the battle pass does differently from the field:**
  - It sets no view (`BTL_battleTickFrame` sets none; the HUD and effects restore `GS_VIEWPOINT` themselves).
  - The origin is `DRAWING_OFFSET` (blended), not the `_COPY` values.
  - The `DR_OFFSET` goes in at `org + 0x20` **elements**, which is byte +0x80, slot 32.
  - The pass calls `renderObjects`. A host-side loop with a skip list was used to bisect the mismatch, then removed.
- **Stock battle frame, from `gpu_frame_dump`:** the world draws with E5 (384, 282), which is `DRAWING_OFFSET` + buffer. The HUD draws after the slot-32 `DR_OFFSET` (160, 120). Two dead ends cost runs:
  - I put the `DR_OFFSET` at byte +0x20. The HP bars dropped out and the hidden clock showed up.
  - I then forced the offset to (160, 120). That moved the world instead.

**The VRAM mismatch was a psxrecomp bug, now fixed (uncommitted).**
- Bisect runs: skip 14 battle objects → 0 mismatches; skip 7 → 106; skip only 0x198 → 0. Object 0x198 (`BTL_renderCommandMenu`) calls `BTL_drawHoveredCommandName` on every render (`src/btl/command_menu.c:229`, `:341-358`). That redraws the command name at VRAM (704,472): `ClearImage` (`src/main/font.c:1526-1531`), then one `LoadImage` per glyph (`:1695-1696`).
- A temporary counter diagnostic, since reverted, showed:
  - The displayed rect restored exactly.
  - Only CPU VRAM differed: 42 px at x 714-715, y 472-481, where two glyph uploads overlap.
  - Before the pass those pixels matched the GPU copy; after it they did not. So guest VRAM really was left wrong.
  - The `ClearImage` never reached the journal, while all 9 glyph uploads were journaled.
- **Cause:** `gpu.c` streams a GP0(A0h) payload into its `vram[]` as the data words arrive. Only at the end does `gp0_commit_cpu_to_vram` hand the rect to the renderer, and only then does `pass_refuse_write` journal it. So the CPU backup is taken after the pass's own pixels are already in place, and the rollback keeps them. The GPU copies are backed up correctly. The pass's glyph buffer starts from the real frame's last cell, so its text differs only where two cells overlap. That is why exactly those 2 columns showed. Any title whose passes upload outside the rect would hit this.
- **Fix:** `gp0_exec_cpu_to_vram` journals the destination when the transfer opens, while `g_psx_render_pass_active` is set, through the new `gl_renderer_pass_note_upload_open`. The commit then finds the rect already covered. Changed files:
  - `runtime/src/gpu.c` (+3 lines)
  - `runtime/src/gpu_gl_renderer.c` (+12)
  - `runtime/include/gpu_gl_renderer.h` (+3)
  - Test stubs: `runtime/tests/gpu_exec_stubs.inc`, `test_gpu_upload_history.py`, `test_gpu_gp0_history_guard.py`
- **Verified:**
  - Battle `PSX_RENDER_PASS_VERIFY=1`: 239 and 276 passes, **0 mismatches**, 0 leaks.
  - Field: 5,430 passes, 0.
  - Guards: `test_render_pass_guards.py` and `test_gpu_upload_history.py --cc clang` pass.
  - `test_gpu_gp0_history_guard.py` still fails to link, but only on 5 symbols its stubs lacked before this change (`gte_nclip_zero_positive`, `psx_cheats_on_vblank`, `gr_texture_banks_supported`, `gr_select_texture_bank`, `mod_texture_bank_live_clut`). Not fixed here.
- Not done: a framework unit test with an A0 upload inside a pass (it needs the GL sandbox), and the runtime ctest suite.

What still steps at 20 Hz: particles and EFE effects (the first pass after each real frame changes 5-9k px), and damage numbers.

Files: `dw_smooth60.c` and the `CMakeLists.txt` hunk. Scripts: `s60.py`, `b60.py` (`--verify`, `--skip`, `--off --gpudump`) and `m60.py s60` in the scratchpad. ## 6d. No added delay, cheaper battles, 2D blending (2026-11-14, uncommitted)

**Pass point moved to `VSync` entry, PENDING.**
- `gameLoop` and `BTL_battleTickFrame` both run `renderObjects`, `DrawSync`, `VSync(3)`, then swap and `GsDrawOt`. At `VSync` entry the previous tick's frame is drawn and waiting for the swap, and this tick's logic is done, so the passes now draw between them before the swap shows anything (`PSX_MOD_RENDER_PASS_FLIP_PENDING`, shown after 1 VBlank).
- This needed `VSync` (`0x80091CA8`) in `game.toml`'s `mod_function_entry_funcs` and a regen. `generate` took 4 s and rewrote 6 shards. The only change in `generated/` is the 2 hook lines per new address (16, then 2 more each for `startSound` and the image calls). Other `VSync` callers (timing polls, other loops) are told apart by return address.
- **Measured** with a new presenter counter, `frame_delay_*` in `render_pass_stats` (psxrecomp, below): host time from the flip that shows a frame to the first present of its pass images. Old pass point (`GsDrawOt`, SHOWN): **50-54 ms**, max 88 ms. New (`VSync`, PENDING): **3-10 ms**, max 15 ms, on the same field, walk and battle stages. Presents held past their planned end dropped from about 1,500-1,900 to about 300 per run.

**Passes draw from the pre-render RAM.** Some render callbacks change state: the fades step their counters, damage numbers advance their bounce. A pass used to re-run `renderObjects` after the stock render, so those ran one step further again. The fades looked a tick ahead for this reason.
- An entry hook on `renderObjects` now keeps RAM, scratchpad and the mod arenas as they are when a stock render starts, the same draw-entry snapshot `render_pass_replay.hpp` uses. Each pass restores it (130-140 µs), then writes the blended values over it.
- That made passes replay one-shot side effects. The field menu's render starts a sound, and `getNextFreeChannel`'s SPU read aborted the pass. A filter on `startSound` returns "no voices" inside a pass.

**2D blending.** Entry hooks on the shared 2D emitters record each stock frame's calls. Inside a pass, each call's screen arguments are blended between the last two stock frames' calls, matched by call site, key and order:
- `renderSprite` and `addFXPrim`: x, y, size and depth;
- `renderParticleFlash`: position, depth, scale and brightness;
- `drawEntityText` and its icon: x and y, keyed by the number's value;
- `renderFade`: the level.

A call with no partner in the previous frame is drawn as the newer frame has it, and so is one that moved more than 96 px. The HUD slide offsets (`CLOCK_OFFSET_X`, `STATUS_UI_OFFSET_X`) are blended from their pre-render values. In a five-round fight with verify on, 15,896 calls were blended, 987 had no partner and 3 were treated as respawned.

**Battle cost.**
- **Interpretation was ruled out.** Staging `overlay_toolchain` so the BTL overlay compiles to native code changed nothing (4.8 ms per pass, and the interpreter ran only about 1.6M instructions in the whole battle).
- **The cost was uploads.** A per-object timer inside the passes found that object 0x198 (`BTL_renderCommandMenu`) took 1.47 ms of a 4.07 ms battle redraw. It redraws the hovered command's name with a `ClearImage` and one `LoadImage` per glyph on every render. A pass replays the stock render from the same RAM, so CPU-to-VRAM uploads outside the drawn rect rewrite what the stock frame already left there, and the sandbox then rolls them back.
- **The fix** is a filter on `LoadImage` and `ClearImage` that skips them inside a pass when they don't overlap the rect. 0x198 dropped to 0.17 ms, and the battle redraw to 2.92 ms. About 10 uploads per battle pass are skipped. What remains is real drawing: three models at about 0.6 ms each, the clock, the map and the EFE engine.
- **Per pass, hidden window, no verify:** battle 4.8-5.0 ms before, 4.0-4.1 ms after. Field went from 2.2-2.3 to 2.5-2.9 ms, with run-to-run noise of about ±0.3 ms; the snapshot restore accounts for 0.14 ms of it. Every wanted pass was granted in both field and battle.

**Plugin bug fixed.** A pass the sandbox rolls back leaves by longjmp, past the end of `pass()`, so the plugin's "inside a pass" flag stayed set after the first abort, and the plugin went quiet for the session. It's now trusted only while a pass is actually running. A forced-abort run (`PSX_RENDER_PASS_WATCHDOG=200000`) shows the frame counter still rising after 8 aborts disabled passes.

## 7. Reply for the player

> The game is built around 20 FPS: logic and drawing tick together every 3 frames, in towns and in battle, and every timer counts those ticks. The "flicker" you see is that 20 FPS stepping, not a bug, and Run Speed makes each step bigger. Felix's Horizon keeps the logic at 20 and draws smoothed frames in between (it needs a 250% CPU overclock and adds up to 50 ms of delay). We now have the same idea working in testing as a launcher option, "Smooth 60 FPS": it redraws the field and battles at 60 on your PC, keeps the game speed exactly as it was, and adds no delay over the original. It works with widescreen, Run Speed, HD texture packs and 1.5, and effects, damage numbers and fades are drawn in between as well. It is not in a release yet.
